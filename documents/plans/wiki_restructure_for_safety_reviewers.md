## 1. 定位与边界

Wiki 是产品知识库，帮助 drug safety scientist / reviewer 完成审查工作，并理解、核查和记录分析结果。专业深度来自数据、证据、方法和局限，不来自软件实现细节。

两个长期稳定的阅读入口：

1. **Complete a review task / 使用指南**：我如何完成工作、在哪里操作、如何保存结果？
2. **Understand data & results / 数据与分析方法**：这些结果代表什么、如何产生、如何核查、哪些结论不能直接推出？

不按“普通用户 / 高级用户”分站，不把专业说明按 developer/admin 角色隐藏。一个 reviewer 可以随时在操作与方法之间切换。可用工具则如实说明取决于当前部署、账号权限和已选 labeling。

### 内容纳入规则

| 内容 | Wiki 中的处理 | 仓库中的处理 |
|---|---|---|
| 任务步骤、输入选择、界面操作、导出 | 保留并重写成工作流 | 仅保留必要的实现说明 |
| 数据来源、范围、版本、频率与证据语境 | 重点补充 | 可以记录数据导入实现 |
| AI 提取、术语匹配、比较与筛查的方法及限制 | 用 scientist 能理解的语言解释 | 保留算法实现与代码引用 |
| 账号权限、某工具为何不可见、任务等待与失败 | 解释用户能采取的行动 | 权限配置、服务排障放运维文档 |
| Python、React、Flask、数据库表、索引、API 路由 | 不进入 Wiki 正文 | `documents/architecture/`、`documents/operations/` |
| Docker、Celery、nginx、环境变量、部署步骤、日志命令 | 不进入 Wiki 正文 | 仓库运维文档 |
| Web-test、内部回归验证流程 | 不作为 reviewer 的工具教程 | 工程验证文档 |
| Set ID、SPL ID、SMILES、MedDRA PT/LLT、查询代码 | 保留；解释其科学或审查用途 | 不因其形式像技术字段而删除 |

例如：Wiki 说“任务在后台执行，可以返回查看状态”；不解释 Celery。Wiki 说“模型选择可能影响提取结果，应核查原文”；不列出连接环境变量。

后续写作证据顺序：实际可操作界面及当前实现 → 用于说明科学方法的原始/权威来源 → 已核对的模块文档 → 旧 Wiki。代码能说明系统做了什么，不能单独证明临床有效性、科学准确性或监管合规。

本次是静态内容与实现审查，不代表对所有工具完成了真实数据端到端验证，也没有验证远程部署的实际数据更新时间。

## 3. 现状结论与优先修正项

### 3.1 信息架构

- 现有 Part I 是基础使用，Part II 是专业工具介绍；两者仍主要围绕功能操作，没有独立的数据与结果解释路径。
- 默认进入登录文章，缺少任务导向首页；长编号目录需要用户先知道工具叫什么。
- 文章选择只在页面 state 中，无法直接分享某篇文章，刷新与浏览器前进/后退不对应阅读位置。
- 搜索只匹配编号、标题、摘要、章节标题与标签，不搜索正文；搜索后的上一页/下一页仍沿完整目录移动。
- 界面使用另一套独立的页头、颜色与大量内联样式；与现在的阅读工作区不够连贯。

### 3.2 内容风险（先纠正，再扩写）

| 发现 | 当前证据 | 重构要求 |
|---|---|---|
| Guest 被描述为可执行全部分析工具 | 实际使用 feature gate 与部署条件过滤 | 不承诺“全部工具可用”；说明权限与个人状态保存的限制 |
| 搜索被描述为返回全部获批产品、全部等效仿制药 | 搜索匹配不等于穷尽数据，也不等于治疗等效性判断 | 分开解释匹配、数据库覆盖、审批/市场类别与等效性，删除过度承诺 |
| 自然语言回答与可复现检索容易混淆 | 现有对话与 Query Builder 是不同入口 | 说明何时只是 AI 回答，何时产生条件并实际查询；要求检查范围和筛选条件 |
| Label View 被统一描述为 PLR、日期被直接称为正式修订日期 | 现有产品存在不同格式、状态和版本字段 | 单独解释显示字段，不能把所有日期视为同一监管事件 |
| AE viewer 宣称版式“exactly as submitted” | 当前 Section View 不复现原发布者完整样式和图片 | 改成准确说明保留/未保留的结构、定位方式与回到来源核查的方法 |
| MedDRA 色彩被解释为层级颜色 | 现有 reader 与 LabelingAE 有不同高亮/标注机制 | 按实际界面图例说明，不混同 SOC 色彩、术语层级与风险等级 |
| PV QC 被写成完整规则式核查 | 当前核心审计聚焦术语判断及引用/语境支持 | 围绕实际输出改写；删除“确保每项问题都被识别”的承诺 |
| QC 与 DrugTox 模块文档自身也有旧描述 | 仓库文字与当前服务职责存在出入 | 不直接搬入 Wiki；逐条核实后再引用 |
| 缺少 FAERS 独立解释路径 | 工具注册表和 label workspace 中均有 FAERS | 新增操作与结果解释，外部科学性表述发布前核对权威来源 |
| 缺少 PGx、Examine、Deep Dive 和版本/申请档案的独立说明 | 当前工具目录已有对应入口 | 补充准确工具选择指南，避免将不同证据用途混为一谈 |
| ChemSearch 描述包含绘图器 | 当前主要输入为 SMILES / InChI / InChIKey | 按实际输入与匹配模式写作，不介绍未提供的绘图操作 |
| Device Intelligence 当作可用功能介绍 | 注册表当前 `enabled: false` | 从核心学习路径下线，不给普通用户展示死入口；发布后再评估附录 |
| FAQ 承诺每月更新、内网自动同步 | 数据源发布节奏不能证明部署实际更新节奏 | 改为如何识别数据范围、版本和可见更新时间；未展示则明确向支持人员确认 |
| label 专属工具链接缺少上下文 | `/pv-profile`、`/labeling-ae` 等不是实际 label 子路由 | Wiki 中引导“先打开 labeling，再从 Toolbox 进入”，或仅在有 label 上下文时提供动作 |
| 近期界面更新未覆盖 | 当前有自适应工具栏、Cards/Table、模型偏好等 | 新截图和步骤必须对应当前版本，区分功能可用性与介绍可阅读性 |

以上属于编辑与产品行为核验发现。涉及 FAERS、频率、RLD/RS、MedDRA、Rule-of-Two 等科学定义时，后续必须核对原始研究、FDA 或相应术语维护机构的正式资料，不以旧 Wiki 的措辞作为依据。

## 4. 新信息架构

### 首页：从审查目标进入

- 全站知识搜索：支持任务、药品标识、界面术语和方法概念；结果标明“Guide / Methods”。
- 主入口：**Complete a review task**、**Understand data & results**。
- 五条精选任务：找对 labeling；核查一个安全性术语；比较历史修订；建立同类产品审查集合；检查包装/标签一致性。
- 一个短的 First review 路径：确认对象和版本 → 定位原文证据 → 选择分析 → 核对结果 → 保存来源。
- 常见问题捷径：工具为何不可见、没有匹配是否意味着不存在、AI 结果如何核查、历史版本为何不可用。
- 不放技术栈、架构图、部署指令、内部服务地址或 developer onboarding。

### A. Complete a review task（使用指南）

| 分组 | 文章方向 |
|---|---|
| 开始审查 | 账号与可用功能；第一次 labeling review；如何选择合适工具 |
| 找到正确审查对象 | 名称/NDC/申请号检索；结构化查询；AI 生成条件及检查；查询代码与复现 |
| 阅读与记录证据 | Label View；原文章节/表格；Toolbox Cards/Table；Notes/项目；导出及来源记录 |
| 组织安全性证据 | FAERS；PV Profile 与 QC；LabelingAE；Examine；DILI/DICT/DIRI/PGx 的选择与使用 |
| 比较与追踪 | 版本历史；FDA Application Profile；LabelComp；Deep Dive；包装/图像审查 |
| 扩展检索 | Chemical Structure Search；结构输入与匹配模式；将结果纳入审查集合 |
| 常见阻碍 | 权限/部署差异、缺失文档、等待/失败/部分结果、导出与复现问题 |

每个分组的工具名沿用当前产品名称。首页以任务引导，文章中保留明确工具名，便于和 UI 对照。

### B. Understand data & results（数据与分析方法）

| 分组 | reviewer 需要得到的解释 |
|---|---|
| 数据与版本 | 数据库范围；标识符；版本与日期；当前/历史状态；原文缺失与替代来源提示 |
| 查询与覆盖 | 名称匹配、Exact match、实体扩展；章节范围；Local/内网差异；结果总数与筛选后总数；无匹配的解释 |
| 安全性术语与证据语境 | AE/ADR、PT/LLT/SOC；高亮和提取的区别；标注对齐；否定、适应证、基础疾病和上下文 |
| 频率与不同证据来源 | labeling 中试验数据、上市后描述与 FAERS 输出的区别；原文分母/人群/剂量/比较组；不要混用不同来源的数字 |
| AI 与质量核查 | 原文、提取、计算和 AI 总结分别是什么；PV QC 实际检查范围；引用与原文核对；不确定和部分结果 |
| 比较与筛查 | 文本变化与科学意义；跨产品可比性；结构相似性指标；器官毒性/PGx 输出；RO2 输入与适用范围 |
| 可追溯与复现 | 保存查询条件、数据库范围、版本标识、筛选状态、结果时间、模型信息及 reviewer 判断；注明产品当前未提供的元数据 |

这里解释“使用者需要理解的处理逻辑”，不进入代码路径、数据库表、SDK 或基础设施。

## 6. 必须新增的内容

优先级 P0：

- First review：从审查问题到可追溯原文证据的一条完整路径。
- 工具选择矩阵：审查目标 → 所需输入 → 推荐工具 → 输出 → 下一步核查。
- 数据库范围、标识符、版本与日期：在开始分析前确认对象。
- 原文、提取、匹配、计算、AI 总结的区别；界面标签不能被误读为同一种证据。
- 当前 Toolbox Cards/Table、搜索/分类/收藏，以及为什么某工具不可见。
- AI Preferences：个人模型偏好、系统默认、可选模型由环境决定；不放 URL/API key/环境变量教程。
- 结果等待、失败和部分完成：如何查看状态、保留已有输出、何时重试或联系支持。

优先级 P1：

- FAERS 的操作与输出解释，独立于 DrugTox。
- PV QC、LabelingAE、标签比较、图像审查的证据核验示例。
- Archived Version Track、FDA Application Profile、Examine、Deep Dive、PGx 各自的用途和适用输入。
- 导出/项目记录清单与术语表。

新增内容必须随当前工具可用性核实，不把待开发能力写成已有功能。

## 7. 文章模板与科学写作规则

### 使用指南模板

1. **Review question**：你要解决什么问题。
2. **Before you start**：对象、版本、数据范围、权限或必要输入。
3. **Steps**：与当前 UI 一致的 3–7 个主要步骤。
4. **What you will see**：真实输出与状态，不做未验证的结果承诺。
5. **Verify and save**：至少一个核查动作和来源记录动作。
6. **If it does not work**：与本任务相关的具体障碍。
7. **Understand the method**：链接对应方法文章。

### 数据与方法模板

1. **What this result means**：一段直接结论。
2. **Source and scope**：数据来源、版本、人群或查询范围。
3. **How it is produced**：概念流程，保留有用的科学术语，不写技术栈。
4. **How to interpret**：字段、单位、比较组和上下文。
5. **What it does not establish**：具体误读边界，不堆砌泛化免责声明。
6. **Reviewer checks**：回到原文/引用/版本进行核查。
7. **References and related guide**：已核对的正式来源与对应操作指南。

写作约束：

- 产品文章沿用英文界面术语；初稿使用 plain English，先解释缩写，不同时扩大成完整双语项目。
- 区分软件能力、科学解释和监管结论；避免“all / exactly / proven / ensures”一类未经证明的措辞。
- 不将查询匹配当作审批、等效性或完整性证明；不将自动 QC 当作保证。
- 数值阈值、频率区间、科学引用与方法来源逐项核实；不从旧文照抄。
- 每篇提供适用范围和最后核验日期；“内容核验日期”与“数据更新时间”分开。
- 示例优先演示如何检查证据，不在 Wiki 中新生成未经验证的药物安全性结论。
- 产品尚未显示的模型、来源或时间元数据，写成“如可见则记录/否则向支持确认”，不虚构界面字段。

## 8. 阅读体验与导航要求

- 首页、指南和方法为同一知识库；两个入口是阅读目的，不是两套重复文档。
- 用稳定的主题地址替代仅靠章节编号；支持刷新、分享、浏览器前进/后退和旧 ID 映射。
- 搜索覆盖标题、摘要、关键词及可检索正文；结果按 Guide/Methods 标记，可跨路径查找。
- 文章提供本篇目录与相关内容；上一篇/下一篇限定在当前路径或明确标明将切换主题。
- 普通科学解释公开可读；工具动作根据当前权限和上下文正确引导，不把全部专业文档当权限页面。
- 有 labeling 上下文时才生成专属工具入口；无上下文时说明从哪里选择对象，不跳到不存在的通用路由。
- 使用现有产品的字体、色彩和边框体系；正文自然滚动，目录吸附，避免内容嵌入狭小滚动框。
- 不保留会暴露内部主机名的界面说明；支持入口使用经过确认的统一渠道。

## 10. 验收场景与质量门槛

### 代表性 reviewer 场景

1. 第一次使用：从首页找到一份 labeling，确认对象/版本并定位一条原文证据，知道如何保存来源。
2. 安全性术语核查：分清原文、高亮与提取结果；能找到方法说明并说明下一步如何核对。
3. 历史修订比较：选择对应版本，理解文本变化与 AI 总结的不同，保留版本标识。
4. FAERS/PV 阅读：知道应该核查哪些来源、上下文与数字，而不是只抄摘要。
5. 工具不可见或分析未完成：找到用户可以采取的行动，不需要理解服务部署。
6. 返回某篇文章：分享链接、刷新和浏览器返回后仍到达正确主题。

### 必须通过的检查

- Wiki 正文不出现安装、建表、容器、服务启动、代理或 SDK 配置教程。
- 所有 28 个旧主题都已迁移、合并、拆分或明确下线；没有静默遗失。
- 已禁用工具不再作为可执行的核心教程推广；专业内容阅读不依赖 admin/developer 身份。
- 所有产品能力陈述都能对应当前界面/实现；科学方法陈述有经核对的正式来源。
- 每个主要工具指南至少有一条方法链接；每个主要方法文章至少有一条操作链接。
- 每个主要输出说明至少交代来源、含义、局限和核查动作。
- 无断链、内部硬编码主机链接、无上下文的 label 专属死入口或旧电脑 `file://` 链接。
- 查询、筛选、版本和导出范围的描述一致；数据更新时间与内容核验日期不混用。
- 1024px 和宽桌面布局可读；键盘搜索、目录、文章链接与焦点可用。
- 最终以真实 reviewer 任务试走验收；静态代码审查或构建成功不能替代科学内容和使用体验验收。
